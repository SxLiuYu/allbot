Run consecutive actions on one screen in one call when the element list already identifies the next targets (e.g. tap a named field, type the whole value, tap another named field, type its value). Choose the step count from the task, up to the per-call limit. Each step is checked locally before the next; the batch stops when an action fails, the interface needs visual review, the app switches, or a step's wait condition is not met. When a step starts loading and the next needs its result, give that step a condition instead of ending the batch: expect (text it brings up), expect_gone (a loading label), expect_app (package or page address) or wait_stable; it waits up to timeout_s (default 8) and stops early on a popup, a system dialog or another app, and the result says how long it waited and why it stopped. Do not batch past a step whose outcome you must judge by looking (which item to pick, whether it worked); end the batch there. A repeated cycle on one screen (swipe to the next item, tap the same control, swipe again) is different: when both targets are already known from the current screen, put 2–4 rounds in one call with x/y from the screen read, and give each round a condition when the screen settles slowly. Keep it short so a failed round is cheap to recover from; do not use a batch when the next target's position or existence needs a fresh look. An unchanged screen alone does not mean the task is stuck. Inspect the final screen before deciding what to do next. All steps must act on the same screen (mixed_surface otherwise). Requested send, post, order, delete and pay actions can be included; read the resulting state before claiming success. Use only refs that were visible before the batch and still identify the same element; if the next target appears only after an action, stop and inspect the new screen.
